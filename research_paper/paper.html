Abstract—Contemporary artificial intelligence (AI) coding assistants operate predominantly in single-user, stateless modalities. When multiple software engineers collaborate on a shared codebase, existing developer tools segregate agent interactions into isolated chat threads, discarding architectural decisions, coding conventions, and collective context across programming sessions. Furthermore, concurrent file writes initiated simultaneously by distributed human developers and autonomous coding agents lead to silent file overwrites and code corruption. This paper presents the architecture, formal design, and empirical implementation of a real-time multiplayer AI coding agent workspace with dual-tier persistent project memory. The system introduces: (1) a multi-tenant room and presence gateway that broadcasts agent reasoning tokens, tool invocations, file alterations, and terminal outputs to all collaborators over full-duplex WebSocket channels; (2) an Optimistic Concurrency Control (OCC) file versioning protocol that prevents silent code clobbering and provides visual three-way conflict reconciliation; (3) a dual-tier persistence engine combining an ACID-compliant relational store (SQLite) with a local, offline Hierarchical Navigable Small World (HNSW) vector index (ChromaDB) powered by a 384-dimensional subword hash embedding model; and (4) an intelligent context builder that selectively injects prioritized project facts and relevance-scored code files into dynamically budgeted LLM context windows. We evaluate the system against our automated test suite comprising 23 unit and integration test suites, demonstrating complete directory isolation, 100% deterministic path-traversal prevention, zero-overhead offline semantic deduplication (δ < 0.10), and real-time multi-client state synchronization under simulated race conditions.

Index Terms—Multiplayer Software Engineering, AI Coding Agent, Persistent Project Memory, Optimistic Concurrency Control, Retrieval-Augmented Generation, WebSocket Synchronization.

I. Introduction

The integration of Large Language Models (LLMs) into modern software engineering has transformed developer productivity through automated program synthesis, test generation, and intelligent code refactoring [1], [10], [11]. However, the prevailing paradigm of AI-assisted software development remains fundamentally solitary and transient. Commercial and open-source coding assistants (e.g., GitHub Copilot, Cursor, OpenHands) execute within isolated local client windows or ephemeral container instances. Consequently, several critical challenges emerge in collaborative team environments:

1) Contextual Isolation: When Developer A instructs an agent to adopt a specific architectural pattern or authentication standard, that decision remains confined to Developer A's ephemeral context window. When Developer B subsequently joins the repository, the agent possesses no historical recollection of prior architectural choices, resulting in contradictory code implementations.

2) Silent Concurrency Clobbering: When multiple human developers and an autonomous coding agent concurrently modify files within a shared workspace, standard file systems overwrite disk buffers blindly. Stale client buffers routinely erase agent modifications, and multi-file agent patches clobber human edits without warning [4], [5].

3) Ephemeral Session Memory: Most developer tools rely strictly on short-term sliding conversational windows. Once an IDE instance restarts or a chat thread is cleared, project facts, debugging discoveries, and design rationales are irreversibly lost [6].

4) Provider Lock-In and Offline Fragility: Many coding assistants depend strictly on commercial cloud inference APIs. If an external API key is revoked or connectivity degrades, development stalls unless an autonomous local fallback mechanism is embedded.

To overcome these foundational limitations, this paper presents the complete technical architecture and implementation of Summit, a collaborative multiplayer web development environment and shared AI coding agent with persistent project memory. Unlike single-tenant assistants, Summit connects multiple distributed developers to the exact same project room governed by one shared AI coding agent.

The primary contributions of this paper are:

• Multiplayer Presence and Shared Agent Event Stream: A centralized WebSocket broadcast bus coordinating presence, streaming agent tokens, tool invocations (read_file, write_file, run_terminal, save_memory, git_checkpoint), and execution states (START, PAUSE, RESUME, STOP).

• Optimistic Concurrency Control (OCC) File Versioning: A monotonic version-tracking protocol that checks expected versus server file versions upon write, returning HTTP 409 conflict payloads and visual difference resolution modals to prevent data corruption during human-agent races.

• Dual-Tier Persistent Memory Engine: An architectural synthesis combining an ACID-compliant SQLite relational database with an offline ChromaDB vector store using a local 384-dimensional n-gram hashing embedding function with cosine deduplication (δ < 0.10).

• Intelligent Context Builder and Memory Extractor: A multi-category prompt budgeting pipeline scoring workspace files by token and topic relevance, extracting enduring architecture decisions while filtering trivial conversational chatter.

• Empirical Verification: Empirical validation across 23 comprehensive automated backend tests and live multi-client collaborative tasks without fabricating external evaluation benchmarks.

II. Related Work

A. AI Coding Agents and Autonomous Program Synthesis: Recent advances in foundation models trained on code, such as OpenAI Codex [1] and CodeXGLUE benchmarks [12], have enabled agents capable of iterative multi-step reasoning. Conversational automated program repair systems [6] demonstrate that multi-turn dialog improves bug fix success rates. However, contemporary agentic architectures execute within single-tenant sandboxes, assuming a solitary user workflow.

B. Collaborative Software Engineering and Concurrency: Collaborative software development has historically relied on asynchronous version control systems (e.g., Git) or synchronous groupware systems [14]. In synchronous editing environments, Operational Transformation (OT) and Conflict-Free Replicated Data Types (CRDTs) [5] resolve character-level conflicts. However, when autonomous agents execute multi-file refactoring operations alongside human programmers, character-level OT introduces extreme operational complexity and semantic inconsistencies. Classical Optimistic Concurrency Control (OCC) [4] provides a robust transaction-validation mechanism that we adapt at the file-version level.

C. Retrieval-Augmented Generation and Vector Indexing: Retrieval-Augmented Generation (RAG) [2] enhances language model generation by querying external knowledge stores. In software engineering, deep code search [7] and knowledge graphs [8] retrieve relevant snippets to ground completions. Dense vector retrieval architectures often utilize Hierarchical Navigable Small World (HNSW) graphs [3] for sub-linear search complexity [16]. While traditional RAG systems rely on heavyweight transformer embedding models, local developer environments require instantaneous initialization and zero-network footprint, which we resolve via offline subword hashing projections.

D. Human-AI Pair Programming Context: Empirical evaluations of developer interaction with AI assistants highlight friction caused by context re-explanation [9], [17]. Programmers frequently express frustration when models forget previously agreed conventions or require repetitive prompt scaffolding [11]. By establishing persistent project-level memory, our system bridges this gap.

III. System Architecture and Design

The overall architecture of the system is organized into three distinct tiers: Collaborative Frontend Clients; FastAPI Gateway and Session Manager; and Core Subsystems comprising the Agent Orchestrator, Dual-Tier Memory, and Sandboxed Workspace Manager (Fig. 1).

Fig. 1. Overall System Architecture: Collaborative web clients connect via WebSockets and REST APIs to the centralized FastAPI server. The SessionManager routes structured events to the shared AI Agent Orchestrator, which queries the Dual-Tier Persistent Memory System and executes safe file operations through the Sandboxed Workspace Manager.

A. Collaborative Web Clients

The user interface is constructed using React 18, TypeScript, Vite, and Monaco Editor. Each developer connects to a designated project room identified by a unique project_id. The client application provides: (1) a live workspace tree and multi-tab file editing with syntax highlighting; (2) a unified live stream displaying agent reasoning traces, markdown chat responses, tool invocations, and terminal outputs; (3) real-time user presence tracking with chromatic identifiers (e.g., Alice in blue, Bob in emerald, Charlie in amber); and (4) a conflict resolution modal rendered whenever a file write encounters a version mismatch.

B. Gateway and Session Management

The backend service is built with FastAPI and Python 3.10+, utilizing an asynchronous event loop (asyncio). Centralized room management is governed by the SessionManager class:

ℛ(p) = { (wsi, ui, ni) ∣ i ∈ [1, Np] } (1)

where ℛ(p) denotes the active connection registry for project p, containing WebSocket handles wsi, user identifiers ui, and display names ni.

When a client establishes a connection to /api/projects/{id}/agent/stream, the session manager registers the socket, persists user metadata to SQLite, and broadcasts a USER_JOINED event containing the comprehensive room occupancy list. Disconnection triggers socket pruning and a USER_LEFT broadcast.

C. Event Normalization Protocol

To maintain protocol uniformity across disparate agent tools, terminal subprocesses, and user interactions, all WebSocket messages conform to a strictly typed schema, AppEvent: 

class AppEvent(BaseModel):
    id: str = Field(default_factory=lambda: str(uuid.uuid4()))
    project_id: str
    type: AppEventType  # USER_JOINED, USER_MESSAGE, 
                        # AGENT_STATUS, TOOL_CALL, 
                        # TOOL_RESULT, TERMINAL_OUTPUT,
                        # FILE_CHANGED, MEMORY_UPDATED
    timestamp: datetime
    data: Dict[str, Any]

The EventNormalizer encapsulates payload formatting, guaranteeing that all collaborators observe identical execution states in sub-millisecond real time.

D. Sandboxed Workspace and Path Traversal Security

To safeguard host environments against directory traversal or file tampering, the WorkspaceManager enforces rigorous boundary checks. For any relative path r, the resolved absolute path Ptarget must satisfy:

Ptarget = resolve(Proot / r),   Ptarget ⊆ Proot (2)

Any attempt to reference parent tokens (e.g., ../) that escapes Proot raises a WorkspaceSecurityError and halts execution immediately.

E. Optimistic Concurrency Control (OCC) Protocol

To eliminate race conditions between concurrent human edits and autonomous agent writes, every file maintains a monotonic version integer v ∈ ℕ initialized at 1 upon creation (Algorithm 1 and Fig. 2).

Algorithm 1: Optimistic Concurrency Controlled File Write
1: Input: Project p, Relative Path r, Content C, Expected Version v_exp, User u 2: Output: (bytes_written, v_new) 3: P = ValidateSafePath(p, r) 4: if v_exp != NULL and FileExists(P) then 5: v_curr = Repository.GetFileVersion(p, r) 6: if v_curr != v_exp then 7: C_server = ReadFile(P) 8: raise FileConflictError(r, v_curr, v_exp, C_server) 9: end if 10: end if 11: WriteAtomicDiskFile(P, C) 12: v_new = Repository.UpdateFileVersion(p, r, C, u) 13: BroadcastEvent(p, FILE_CHANGED(r, v_new)) 14: return (Length(C), v_new)
Fig. 2. Optimistic Concurrency Control (OCC) Workflow: Server validates expected versus current versions. On mismatch (vserver ≠ vexpected), HTTP 409 halts the write and summons the client resolution modal.

When a conflict arises, the server returns HTTP 409 with the authoritative server version and content buffer. The client UI renders a comparison modal offering two deterministic resolution paths: (1) Accept Server State (discards stale buffer and reloads vserver); or (2) Force Overwrite (issues an unconditional write with vexp = NULL, establishing vserver + 1).

IV. Methodology and Implementation

A. Shared Agent Orchestration and Tool Invocation

The agent execution pipeline is managed by SummitAdapter. When a user posts an instruction, the adapter coordinates execution using a multi-turn reasoning loop capped at 10 turns.

1) Model-Agnostic Dispatching via LiteLLM: The adapter integrates litellm to interface transparently across heterogeneous AI providers: Groq (llama-3.3-70b-versatile, deepseek-r1-distill-llama-70b, llama-3.1-8b-instant), Google Gemini (gemini-2.0-flash), OpenAI (gpt-4o), and Anthropic (claude-3-5-sonnet-20241022). If no API keys are present, the system activates an offline deterministic fallback engine that parses workspace files and executes tests without failure.

2) Sandboxed Tool Set: The agent is equipped with five standardized tools declared via JSON schema function calling: read_file(path), write_file(path, content), run_terminal(command), save_memory(key, value, category), and git_checkpoint(message).

3) Lifecycle State Control: Execution states include IDLE, THINKING, RUNNING, PAUSED, STOPPED, and ERROR. Developers can pause the agent mid-task via an asynchronous asyncio.Event, inspect partial changes, resume execution, or terminate runaway runs via asyncio.Task.cancel().

Fig. 3. Multiplayer Sequence Diagram: Alice initiates a collaborative coding instruction. The shared AI agent streams thoughts, tool invocations, and test executions simultaneously to Alice and Bob. Concurrently, Bob attempts an edit against an outdated buffer, triggering OCC conflict interception and resolution.

B. Dual-Tier Persistent Memory System

The memory architecture addresses relational reliability with transactional integrity alongside fuzzy semantic retrieval with deduplication by coupling SQLite with ChromaDB (Fig. 4).

Fig. 4. Dual-Tier Persistent Memory Lifecycle: The extraction engine filters trivial noise, classifies persistent facts, enforces semantic deduplication via ChromaDB (δ < 0.10), persists to SQLite, and dynamically budgets context for downstream agent runs.

1) Tier 1: Relational Source of Truth (SQLite): Structured entities are managed using SQLAlchemy 2.0 ORM over SQLite: projects (workspace registry), conversation_messages (chronological transcripts), project_memories (architectural rules, conventions, facts), agent_runs (execution logs), and file_changes (OCC version logs).

2) Tier 2: Semantic Vector Store (ChromaDB): To enable semantic similarity search without external dependencies, we implement LocalEmbeddingFunction. For text T, tokens and character trigrams are projected into a normalized dense vector v ∈ ℝ384:

vk = ∑t [ wt / √(pos(t) + 1) ] · 𝕀(hash(t) ≡ k (mod 384)) (3)

followed by L2 normalization:

v̂ = v / (∥v∥2 + ε) (4)

Vector distance is evaluated in cosine space using an HNSW graph index: Dcosine(u, v) = 1 - (u · v).

3) Semantic Deduplication Protocol: Before inserting a memory item, ChromaDB queries the closest existing document. If Dcosine(unew, uexisting) < 0.10 and categories match, the existing memory is updated in place rather than duplicated (Algorithm 2).

Algorithm 2: Memory Storage with Semantic Deduplication
1: Input: Project p, Content C, Category T, Importance I 2: Output: Stored ProjectMemoryItem 3: H = ChromaDB.Search(p, query=C, top_k=1) 4: if H is not empty then 5: d = H[0].distance 6: T_hit = H[0].metadata.memory_type 7: if d < 0.10 and T_hit == T then 8: doc_id = H[0].id 9: return UpdateMemory(p, doc_id, C, T, I) 10: end if 11: end if 12: R = SQLite.InsertMemory(p, C, T, I, is_active=True) 13: ChromaDB.AddDocument(R.id, C, metadata={p, T, I}) 14: return R

C. Intelligent Context Builder and File Scorer

The ContextBuilder implements a structured prompt assembly algorithm:

• Memory Categorization and Priority Sorting: Active memories are retrieved and sorted by hierarchical category weight ωcat and importance I: SortKey(m) = (ωcat(m.type), -m.importance), prioritizing architectural decisions (ω=1) and coding conventions (ω=2) over bug fixes (ω=4) and project facts (ω=5).

• Budget Constraint Enforcement: Formatted markdown representation of memories is capped at 2,500 characters, truncating lower-priority items when exceeded.

• Codebase File Relevance Scoring: Candidate workspace files f are evaluated against user prompt q via heuristic scoring:

Score(f, q) = 15·𝕀(pf ∈ q) + 10·𝕀(nf ∈ q) + 4∑𝕀(k ∈ nf) + 2∑𝕀(k ∈ pf) + 5·𝕀topic(f, q) (5)

where pf is path, nf is filename, and k represents prompt keywords. The top 4 scored files (capped at 6,000 characters each) are embedded into the prompt.

D. Memory Extractor and Noise Filter

Following task completion, MemoryExtractor inspects prompts, outcomes, and modified files. An empirical regex filter is_trivial(text) discards ephemeral phrases (e.g., "ok", "run pytest", "fix this file", length < 10 chars). Non-trivial events undergo structured classification, writing lasting rules to persistent memory.

C. Concurrency and Conflict Interception Evaluation

The OCC mechanism was verified under simulated race conditions in test_multiplayer_memory.py. File main.py was initialized at v=1. Collaborator A submitted an edit with expected version vexp=1, successfully incrementing the server version to v=2. Collaborator B concurrently submitted a write with stale expected version vexp=1. The WorkspaceManager detected the disparity (vcurr = 2 ≠ 1) and raised FileConflictError, causing the endpoint to return HTTP 409 Conflict with server buffer intact, confirming zero silent clobbering.

D. Security and Path Traversal Prevention

The security sandbox was verified in test_workspace.py. Invocations attempting directory traversal (e.g., ../../outside.txt, ..\..\windows\system32\calc.exe, /etc/passwd) were intercepted by validate_safe_path(), raising WorkspaceSecurityError in 100% of test cases.

E. Offline Vector Store and Deduplication Validation

Vector operations were verified in test_chroma_store.py. Cross-session persistence confirmed documents remain retrievable across client restarts. Project isolation demonstrated that searching within Project A never retrieves documents from Project B. Near-duplicate memory insertions (Δcosine < 0.10) triggered updates rather than duplicate records, bounding vector store growth.

F. Proposed Future Evaluations

While the architecture has been thoroughly verified through unit and integration tests, large-scale multi-team human-subject longitudinal studies have not yet been conducted. We explicitly identify systematic human-in-the-loop developer velocity benchmarks, comparative pass@k metrics across multi-agent vs. single-agent teams, and latency scaling beyond 50 concurrent room collaborators as proposed evaluations for future work.

VI. Discussion and Limitations

A. Architectural Tradeoffs: Our design prioritizes file-level OCC over character-level Operational Transformation (OT) or CRDTs. While OT allows concurrent typing within the same line, autonomous coding agents perform coarse-grained, multi-line AST refactoring. Merging human keystrokes mid-generation during an agent tool write frequently corrupts program syntax. OCC provides a crisp transactional boundary that alerts the developer before broken syntax is committed.

The 384-dimensional n-gram hashing embedding function guarantees 100% offline availability and sub-millisecond indexing with zero external downloads. However, hash-based embeddings lack the deep contextual semantics of dense transformer embeddings. For complex semantic domains, hybrid search combining BM25 and dense embeddings represents a promising optimization.

B. Current Limitations: (1) The terminal runner executes directly within the host environment; untrusted cloud deployments require containerized Docker or Firecracker microVM sandboxes; (2) The agent executes turns sequentially per project room; concurrent complex instructions are queued rather than handled through bifurcated parallel sub-agents; (3) Monolithic files (>10,000 lines) are truncated at configured caps (6,000 characters) to respect LLM context budgets.

VII. Conclusion and Future Work

In this paper, we introduced the architecture, design principles, and implementation of a multiplayer AI coding agent with persistent project memory. By replacing solitary, ephemeral chat windows with a collaborative WebSocket presence hub, developers interact with a single shared AI coding agent that maintains continuous awareness of collective programming activities. Our Optimistic Concurrency Control protocol prevents silent code corruption during concurrent human-agent editing, while our dual-tier persistence engine (SQLite and ChromaDB) ensures that architectural decisions and coding conventions survive across programming sessions without runtime cloud dependencies. Empirical testing across 23 unit and integration suites validates that the system provides secure workspace isolation, zero-overhead offline semantic deduplication, and resilient real-time synchronization.

Future work will expand upon these foundations by: (1) integrating containerized Firecracker microVM sandboxes for untrusted terminal execution; (2) incorporating fine-grained AST-aware merge drivers for automated three-way file conflict resolution; (3) introducing multi-agent specialization where distinct architectural, testing, and documentation sub-agents collaborate within the shared room; and (4) conducting longitudinal user studies with professional software engineering teams to measure impact on team velocity and architectural consistency.
